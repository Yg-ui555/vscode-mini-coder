# Mini-Coder

> 一个为中文开发者优化的 VS Code AI 编程助手。
> 核心不是"能聊天"，而是**能证明自己是对的**。

[![TypeScript](https://img.shields.io/badge/TypeScript-5.3-blue)](https://www.typescriptlang.org/)
[![VS Code](https://img.shields.io/badge/VS%20Code-1.86%2B-007ACC)](https://code.visualstudio.com/)
[![License](https://img.shields.io/badge/license-MIT-green)](LICENSE)

---

## 它解决什么问题

AI 编程助手最典型的失败**不是"没改对"，而是"改对了目标、把别处改坏了"**。

而这个 bug agent 自己发现不了 —— 它跑一次测试，看到绿色，就收工了。

Mini-Coder 的主要工作，就是**把这类失败变成可见、可测量、可修复的东西**。

## 三个设计决策

这一节比功能列表重要得多。它回答的是"你为什么这么做"，而不是"你做了什么"。

### 决策 1：评测用 baseline→after 三方比对，而不是"跑通就行"

每道题的流水线：

```
1. 复制初始代码到独立沙箱          ← 题与题零污染
2. 跑一遍 check.js →【baseline】  ← 知道哪些 case 本来就是过的
3. 让 agent 在沙箱里干活
4. 再跑一遍 check.js →【after】
5. 三方比对：
     baseline 过 + after 过  →  保持通过
     baseline 挂 + after 过  →  达成（本题要的）
     baseline 挂 + after 挂  →  没达成
     baseline 过 + after 挂  →  ⭐ 回归！agent 把对的改坏了
```

只统计"最终有没有过"的话，**回归这类失败 100% 被掩盖**。

### 决策 2：断言必须可自动判定，且每题配人写的标准答案

**不许用 LLM 打分。** LLM 给自己打分就是自我麻醉 —— 你出一道题，LLM 说做对了，你就信了。

所以：

- 每条断言是二值的（抛异常 / 不抛）
- 每题至少 2 个 case 在初始代码上就通过（回归守卫，否则 L4 是摆设）
- 每题至少 1 个 case 在初始代码上必须挂，且对应任务明确要求的新增能力
- **每题配一份 `oracles/*.solution.js` 标准答案**，`npm run eval:solvable` 跑一遍，
  要求全部 case 一个不挂 —— 证明题目不是废题

> 这条是踩过坑才加的。真实教训：第二批评测跑出 2 处回归，
> 逐条核对发现**全是断言写错了** —— agent 调 `record_note` 往 `.notes/` 写错题本，
> 那是产品的正常功能，而我的断言写着"这个目录一个字节都不能动"。
>
> **测量工具的 bug 比被测对象更可怕**：agent 做对了被判成失败，pass rate 掉下来，
> 第一个反应会是"模型变差了"，于是去调提示词、换模型 —— 全在错误方向使劲，
> 真正的 bug 反倒被藏了起来。

### 决策 3：中断时补齐 tool_call，而不是删掉它

OpenAI 兼容协议规定：assistant 声明了 N 个 tool_call，就必须跟 N 条 tool 消息，
一一对应，缺一条直接 400。

**两个真实的 400 场景**：

1. AI 一次调多个工具时用户点「停止」→ 剩余 tool_call 永远没有回应 → 孤儿
2. autocompact 压缩历史时，把 assistant 和它后面的 tool 消息**拆散** → 结构非法

后者更严重：中断要用户主动点停止才触发，而压缩在**任何长对话里必然触发**。

**修法是两层防御，缺一不可**：

| 层 | 位置 | 作用 |
|---|---|---|
| 治本 | `agent/loop.ts` 中断时补齐**剩余全部** tool_call | 不让新的坏记录产生 |
| 治旧 | `util/historyRepair.ts` 读会话时自愈 | 救回磁盘上已存在的坏记录 |

> ⚠️ 这里踩过一个坑：**光把孤立 tool 消息的内容换成说明是没用的。**
> 协议校验的是 `tool_call_id` 有没有对应的 `tool_call` 声明，跟内容写成什么毫无关系。
> 唯一既能保留信息、又协议合法的做法，是**补一条合成的 assistant 声明**把它们兜住。

### 附带的原则：绝不让模型重复执行已有副作用的操作

如果某个工具可能已产生外部副作用（git push 发出去了、文件被删了），
而我们悄悄把它的调用记录删掉，模型下一步很可能**再做一遍** ——
问题就从"做了一次"变成"做了两次"，而用户毫无察觉。

所以正确做法永远是**显式告知**：「这一步没执行完」，由模型自己决定要不要重试。

## 决策 4：优化必须有「前后对比」，而且要量出测量误差

只报「pass rate 从 94% 到 100%」是没用的 —— 因为：

1. **pass rate 已经饱和**，改 prompt / 换模型数字都不动，失去反馈信号
2. **单次运行的噪声极大** —— 实测同一批题，单次 token 能从 **-67% 波动到 +233%**

第 2 点是 Phase 1 改造时真实撞上的。我们做了三项优化后跑了一次评测：

| 题目 | 轮数 | token | 变化 |
|---|---|---|---|
| 22-adversarial-todo-bait | 12 → 5 | 58,167 → 19,062 | **-67.2%** |
| 27-adversarial-hidden-dir-trap | 17 → 7 | 101,729 → 35,058 | **-65.5%** |
| 18-hard-deep-locate | 15 → 8 | 92,182 → 42,363 | **-54.0%** |
| 05-simple-parse-config | 11 → 6 | 56,744 → 26,379 | **-53.5%** |
| … | | | |
| 21-adversarial-ambiguous-optimize | 6 → **14** | 21,528 → 71,717 | **+233.1%** 😱 |

只看 21 号题，会得出「我的优化让某些题恶化了 233%」的结论。
**但那是噪声，不是信号** —— LLM 每次跑的路径都不一样。

### 解法：重复运行 + 变异系数 + 显著性判定

```bash
npm run eval -- --repeat 3        # 每题跑 3 次，输出方差报告
```

| 题目 | 通过率 | token 均值 | 标准差 | cv | 波动 |
|---|---|---|---|---|---|
| … | 100% | 35,058 | 12,430 | 35.5% | ⚠️大 |

- **cv（变异系数）** = 标准差 / 平均值 —— 去掉量纲，能横向比较不同量级的题
- **cv > 15%** 的题，单次对比得出的差异**不可信**，必须跑多次看分布
- 判定标准：差异 > 2 倍标准差 → 大概率是真差异；< 1 倍 → 大概率是噪声

> **这是本项目最容易被忽略、但面试时最能体现工程素养的一点：**
> 不是「我优化后数字变好了」，而是「**我知道自己的测量有误差，所以我用统计方法证明了优化是真的**」。
>
> 对比一下：goose 用「脚本化假 Provider」测**流程逻辑**（确定性、零成本），
> 我们用「真跑 N 次」测**模型能力**的分布（贵、有噪声，但这是唯一能回答
> "我的 prompt 改动到底有没有让模型变强"的方法）。两者互补。

### Phase 1 的实测收益

**两次独立全量运行**（基线 commit `6bb6b92` → 本轮）：

| 指标 | 基线 | 本轮（第 1 次） | 本轮（第 2 次） | 变化 |
|---|---|---|---|---|
| Pass Rate | 100% | 100% | 100% | 持平，**0 回归** |
| 总 token | 1,113,577 | 985,245 | 981,822 | **-11.5% / -11.8%** |
| LLM 调用数 | 203 | 173 | 175 | **-14.8% / -13.8%** |
| 总耗时 | 425.8s | 369.5s | 348.5s | **-13.2% / -18.1%** |
| 总成本 | ¥2.545 | ¥2.273 | ¥2.248 | **-10.7% / -11.7%** |

> ⭐ **为什么报两次而不是挑好看的那次**：
> 前面刚证明了单次运行的噪声能到 ±233%。
> 只报一次、只报好的那一次，跟没做方差统计是一回事 ——
> **自己的项目也得守自己的规矩。**
> 两次独立运行都落在 -11.5% ~ -11.8% 这个区间，
> 这个「区间」才是可信的结论。

基线存档在 `eval/baselines/`，按 commit 命名（`baseline-6bb6b92.json`）——
**每个数字都能追溯到它对应的代码版本**。对比表见
[`compare-6bb6b92-vs-phase1.txt`](eval/baselines/compare-6bb6b92-vs-phase1.txt)。

### 决策 5：pass rate 饱和了怎么办 —— 补题 + 换信号 + 消融

Phase 1 结束时 18 道题全过，pass rate 顶到 100%。
**这时候任何优化都没法证明效果** —— 因为你没有能动的尺子。

Phase 2 做了三件事：

**① 补 5 道真难题**（18 → 23）：真实 `tsc` 编译、5 个调用点的异步迁移、
内部契约变更但对外契约不变、性能优化但行为逐字节不变、加新功能却改坏上游契约。
每道题都配了**人写的标准答案**，证明题目有解（否则它会以"满分率下降"的形式把你引向错误方向）。

**② 换一个更细的尺子** —— case 级「目标 case 修好率」：

任务级 pass rate 只有 0/1 两档，**修好 1 个 case 和修好 15 个 case 都是 100%**。
新指标把分母换成「baseline 挂掉的 case 数」：

```bash
npm run eval -- 31 32 33 34 35
# 目标 case 修好：28/28（100%）  ← 比任务级 pass rate 更细一档的信号
```

**③ 消融实验 —— 回答"这题到底在测什么"**

```bash
npm run eval -- --ablate grep,run_shell
```

把工具从 agent 的清单里**摘掉**（它连这个工具存在都不知道），看题还过不过。
结果给出了三个诚实的结论：

| 配置 | Pass Rate | 目标 case | 成本 |
|---|---|---|---|
| 全量工具 | 100% | 28/28 | ¥1.57 |
| 摘掉 grep | 100% | 28/28 | ¥1.18 |
| 摘掉 grep + run_shell（**一次命令都跑不了**） | 100% | 28/28 | ¥1.32 |

- 这几道题**不测"会不会用 grep"** —— 沙箱只有 5-9 个文件，通读就够
- ⭐ 消融本身有个**漏洞**：`run_shell` 是后门。摘掉 grep 之后，
  agent 转头就跑了 `grep -rn ...`（shell 版）。**能力一点没少**
- ⭐⭐ 就算**一次命令都跑不了**，agent 依然全过 —— 这几道题考的是
  **代码理解 + 推理**，不是工具使用

> 最后一个发现还牵出一个真问题：**评测轨迹以前不记录工具参数**
> （`args` 恒为空对象），只看得到"调了 36 次 run_shell"，
> 分不清跑的是 `ls` 还是 `grep` —— 而这两种结论完全相反。
> 现在 `summarizeArgs()` 把它记下来了。

## 四个特色

### 1. 自动跑测试 + 自动修

保存文件后自动触发：

| 你改了什么 | 会发生什么 |
|---|---|
| 测试文件 | 直接跑这个测试文件 |
| 源代码 | 找出引用了它的测试，只跑那些（找不到就不跑，避免假绿灯） |
| 连续保存多个文件 | 1.5 秒防抖，合并成一次 |

跑完失败会问「要不要 AI 自动修」，修完**按退出码**重新验证
（不是 `includes('passed')` —— 那种写法在 `3 failed, 5 passed` 上永远判通过）。最多修 3 轮。

### 2. 中文 commit 规范

`功能:` / `修复:` / `文档:` / `重构:` / `测试:` / `样式:` / `杂项:`

### 3. 错题本自动归档

`.notes/2026-10-23.md`：

```markdown
## 16:37 ⭐ 修 autoTest 的 includes(passed) 误判

原来判断用的是 output.includes("passed")，但 pytest 失败时输出是
"3 failed, 5 passed"，这行字里就有 passed，于是永远判定通过。

**改动**：
- `autoTest.ts` — didTestsPass 改用退出码

**踩到的坑**：
- 同一个文件里 :82 的注释写了不能用 includes 判断，:276 又犯了一次

**测试**：vitest → 16 passed
```

富条目由 AI 通过 `record_note` 工具在任务结束时写入（只有它知道原因和坑）。

### 4. Hook 机制：把「自动跑测试」从功能升级成平台能力

原来的自动测试是一条**写死的链路**（文件监听 → 防抖 → 找测试 → 跑 → 提示 AI 修）。
想再加「改完自动跑 lint」「提交前检查」，就得去改 `autoTest.ts` —— 加一个功能就多一处硬编码。

Hook 机制把它改成 **4 个生命周期点 + 声明式配置**：

| Hook | 时机 | 能阻断吗 | 干什么 |
|---|---|---|---|
| `PreToolUse` | 工具调用前 | ✅ | 否决危险操作（理由回给模型，它会换策略） |
| `PostToolUse` | 工具调用后 | ❌ | 通知 / 副作用（格式化、审计日志） |
| `Stop` | 回合结束前 | ✅ | **测试没过就不许收工** |
| `UserPromptSubmit` | 用户发消息后 | ❌ | 注入上下文（当前分支、待办） |

在工作区放一个 `.vscode/mini-coder-hooks.json` 就能用：

```json
{
  "hooks": {
    "Stop": [
      { "matcher": ".*", "hooks": [{ "type": "command", "command": "npm test" }] }
    ],
    "UserPromptSubmit": [
      { "matcher": ".*", "hooks": [{ "type": "command", "command": "git branch --show-current" }] }
    ]
  }
}
```

`Stop` hook 的语义是「**agent 说"我做完了"，但 hook 说"不许结束"**」：
测试挂了 → 把失败输出回灌给模型 → 它继续修 → 连续 8 次还不过才强制放行（防死循环烧钱）。

这正好治了 AI 编程助手最典型的病：**它声称改好了，其实没改对，而它自己发现不了**。

三条铁律：

1. **hook 自己出错永远不阻断主流程** —— 脚本不存在、崩了、超时，只记日志。
   只有 hook **明确返回非 0 退出码**才算否决。
   （这里踩过一个坑：Windows 的 cmd.exe 报错是 GBK 编码的，Node 按 UTF-8 解码出来是乱码，
   靠文本匹配根本认不出"命令不存在"—— 改成主动探测可执行文件才解决。）
2. **只有 `PreToolUse` 和 `Stop` 能阻断**，另外两个只能"说两句"。
3. **Stop 的连续阻断有上限（8 次）**。

内置的「测试没过不许收工」用设置项 `mini-coder.hooks.stopAutoTest` 开启，
复用现成的 `autoTest` 测试执行逻辑 —— 它就是这套机制的第一个消费者。

## 权限：它在多大范围内能动你的代码

| 档位 | 改文件 | 跑 shell | 适合什么时候 |
|---|---|---|---|
| **只读** | 直接拒绝 | 直接拒绝 | 当「能读整个仓库的搜索引擎」用 |
| **写入需确认**（默认） | 弹窗确认（含 diff 预览） | 只在命中高危特征时确认 | 日常写代码 |
| **全部需确认** | 弹窗确认 | **每一条都确认** | 只想让它跑构建和测试 |

两条不变的规则：

- **只读操作在任何档位都不弹窗。** 每读一个文件弹一次窗，用户的反应不是"更安全了"，
  而是"烦死了全关了"，安全反而形同虚设。
- **改文件永远有 checkpoint 存档**，改错了 `/undo` 一键退回。

> 为什么不学 goose 的 LLM-as-judge 权限判定（每次调用多一次完整 LLM 往返）？
> 慢、烧钱，而且判错的方向恰恰是最危险的方向。这里用 `ToolMeta.kind` 静态判定。

## 架构

```
src/
├── agent/
│   ├── loop.ts            ReAct 主循环（迭代上限来自 limits.ts）
│   ├── provider.ts        OpenAI 兼容流式 Provider（手写 fetch + SSE）
│   ├── limits.ts          硬限制单一真相源 ⭐
│   ├── context.ts         system prompt 拼装（含技能索引 + AGENTS.md）
│   ├── toolOutputStore.ts 大输出外置 ⭐
│   ├── hooks/               4 个生命周期点（PreToolUse/PostToolUse/Stop/UserPromptSubmit）⭐
│   └── tools/             9 个工具 + 工厂 + 元数据 + 路径白名单 + 三档权限
├── session/               JSONL 持久化 + 中断续跑快照
├── skills/                技能包渐进式加载 ⭐
├── features/              三个特色（autoTest / zhCommit / notes）
├── eval/                  评测框架（23 题，L4 回归检测 + 消融实验）
└── util/                  token 计数 / 成本 / diff / 历史自愈
```

**几个关键抽象**：

- **工具定义只有一份**（`agent/tools/factory.ts`）—— 面板 / 评测 / 自检 / 自动修四处共用。
  曾经散落在 4 处，漏一处就出现"聊天里能用、评测里用不了"的失真。
- **权限决策只有一处**（`agent/tools/approval.ts` 的 `approveToolCall()`）——
  曾经散在 4 个工具里，加档位必然漏。
- **迭代上限只有一处**（`agent/limits.ts`）—— 修掉"LLM 被告知 30 轮、实际只给 20 轮"，
  这个 bug 不会崩，只会让模型前期不主动收尾。
- **hook 配置只有一处**（`agent/hooks/`）—— 4 个生命周期点的调度集中在一处，
  加新 hook 点不用改 agent 主循环以外的地方。
