# Mini-Coder 面试问答准备（12 题）

> **怎么用这份文档**
>
> - 每题给**答题骨架**（骨架 = 你必须说到的点），不是逐字稿。
>   逐字稿念出来会像背书，面试官一听就知道。
> - 每题给**加分点**（能讲出来就是加分，讲不出来不扣分）。
> - 每题给**可能的追问**和应对。
> - ⚠️ 涉及数字的地方，**面试前跑一遍**确认，别背旧数。
> - 🔥 标了 🔥 的是**必答题** —— 面试官不问，你也要主动带出来。

---

## 1. 🔥 "你怎么知道你的 agent 是对的？"

**骨架**（四层，缺一层就掉档）：

1. **baseline→after 三方比对** —— 每道题跑两遍 check：
   `baseline 挂 + after 过` = 达成；`baseline 过 + after 挂` = ⭐**回归**。
   只看"最终有没有过"的话，**回归这类失败 100% 被掩盖**。
2. **人写的标准答案（oracle）** —— 每题配一份 `oracles/*.solution.js`，
   执行它之后要求全部 case 一个不挂。
   **目的不是检查 agent，是检查题目本身是不是废题。**
   废题会以"满分"的形式混进评测集 —— agent 做对了却拿不到分，
   你看到 pass rate 掉了，第一个反应会是"模型变差了"，全在错误方向使劲。
3. **消融实验** —— 把工具从 schema 里摘掉再跑，看题还过不过，
   用来回答"这套题到底在测什么"。
4. **方差统计** —— 重复跑 N 次算变异系数，判断差异是不是噪声。
   单次运行的结论不能当结论（我的消融实验里噪声能到 3%）。

**核心观点句**：

> "我的观点是：**评测的价值不在于分数高，在于分数能指导下一步。**
> 之前我的题跑出来 100% 全过 —— 这恰恰说明尺子坏了。
> 所以我做了消融，发现摘掉 grep 之后还是 100%，
> 直接告诉我下一批题该往哪出（规模型，41-44）。"

**可能的追问**：
- "为什么不让 LLM 打分？" → **LLM 给自己打分就是自我麻醉**。
  每条断言必须是二值的（抛异常/不抛），人写标准答案做交叉校验。
- "30 道题是不是太少？" → 分三档（普通/困难/对抗），
  对抗档专门测"agent 该拒绝的时候有没有拒绝"。

## 2. 🔥 "上下文超长怎么办？"

**骨架**（五个手段，每个说清"为什么需要它"）：

| 手段 | 一句话 | 为什么需要 |
|---|---|---|
| **双可见性** | 压缩不删历史，只打 `agentVisible=false` 标记 | 用户还能回看"agent 当时看到了什么"；物理删除不可逆 |
| **分组保护** | assistant + 它后面所有 tool 消息当成**一个整体**保护 | 拆开就是 400，而且 autocompact 在**任何长对话里必然触发** |
| **渐进式技能加载** | 默认只给一行索引，模型要了才给正文 | 技能包全文塞进 system prompt 是纯烧钱 |
| **大输出外置** | 超大工具输出落盘，只回灌头尾预览 + 文件路径 | ReAct 每步重发全上下文，大输出会被重复发几十次 |
| **子智能体隔离** | 大范围调查派子 agent，只回结论 | 主上下文增量 < 500 token，而不是几万 |

**⭐ 必须主动说的一条**：

> "双可见性**不能只打标记不过滤** —— 那样 token 一分钱没省，
> 而且模型会同时看到互相矛盾的历史（摘要说'改完了'，下面却挂着没压掉的原始对话）。
> 所以请求前必须 `filterForModel()` 过滤。"

**可能的追问**：
- "压缩的阈值怎么定的？" → 占上下文窗口 **70%**（借鉴 goose `check_if_compaction_needed`）。
  留 30% 余量是因为一次工具调用可能就要塞几万 token。
- "按字符还是按 token 算？" → **按 token**，而且中英文分开估算。
  同样 8 万字符，全英文约 2 万 token，全中文约 6 万 token，误差 3 倍。
  估少了白丢历史，估多了会被 API 直接 400、整轮崩掉。

## 3. "它怎么保证不改坏东西？"

**骨架**：

1. **写前审批** —— 写操作按权限档位弹确认，带 diff 预览。
2. **checkpoint 快照** —— 改之前把涉及的文件的旧内容存下来。
3. **一键回滚** —— `/undo` 撤回最近一次修改。

   比喻：**事前知情（审批 + diff）— 事中留痕（checkpoint）— 事后可撤（rollback）**，构成完整闭环。

4. ⭐ **权限用静态元数据，不用 LLM-as-judge**（这条要主动讲，见第 11 题）。

**可能的追问**：
- "审批每次都弹很烦怎么办？" → 三档权限（只读 / 写入需确认 / 全部需确认），
  用户可以切；而且只读工具（read/grep/glob/list_dir）完全不弹。
- "为什么不学 goose 用 LLM 判断危不危险？" → 见第 11 题。

## 4. "它怎么知道做完了？"

**骨架**：

- **Stop hook** —— agent 说"我做完了"的时候，先跑一遍项目测试，
  没通过就把它**打回去继续干**。内置实现叫"测试没过不许收工"。
- 用户可以自己写 `.vscode/mini-coder-hooks.json` 定制（4 个生命周期点：
  `UserPromptSubmit` / `PreToolUse` / `PostToolUse` / `Stop`）。
- **连续阻断计数**：Stop hook 连续拒绝 8 次后强制放行 ——
  防止"测试永远修不过 → 无限循环"。

**⭐ 加分点**（这个坑很值得讲）：

> "插一句：我曾经写错过 Stop hook 的调用签名 ——
> 执行器是 `runStop(response, cwd, iteration)`，我传成了 `runStop(response, iteration)`，
> **轮次号被当成工作区路径传给了 spawn**，Node 直接抛 `ERR_INVALID_ARG_TYPE`。
> 也就是说这个功能上线以来一次都没成功运行过。
> 教训是：**一个没人验证过的功能，等于不存在。**
> 所以我现在 hook 路径有专门的回归测试。"

## 5. 🔥 "多步任务的状态怎么管？"

**骨架**：

1. **状态独立于消息历史** —— 待办清单存在 session 里（不是存在对话消息里）。
   借鉴 goose 的 `session/extension_data.rs`：**状态存 session，不存消息流**。
   因为消息流会被压缩，状态不会。

2. **每轮重建注入，不是追加** —— 每轮请求前把**当前**待办状态重新渲染成一条 system 消息，
   **替换**掉上一轮的那条。

   > ⚠️ 必须是替换不是追加：追加的话上下文里会堆 N 条历史快照，
   > 而 ReAct 每步重发全上下文 —— 纯烧钱，而且模型会看到互相矛盾的历史状态。

3. **UI 三态渲染** —— ☐ pending / ▶ in_progress / ☑ completed + 顶部进度条。

4. ⭐ **压缩不丢**（这是本项目的核心验收点，**一定要主动讲**）：

> "这里我踩过一个真 bug：压缩逻辑会把所有'纯对话消息'送去总结并标记为模型不可见，
> 而待办状态正好是 `role: 'system'` 的消息，落在这个分类里。
> 更麻烦的是 `filterForModel` 会**永久**过滤掉这类消息 ——
> **压缩一次之后，模型就再也看不到待办状态了**，多步任务必然从头再来。
>
> 修法是加了一个通用机制：消息打 `pinned: true` 就永不参与压缩。
> 比喻：白板上的'本季度目标'不会被保洁擦掉，因为它是**当前状态**不是**历史记录**。
>
> 为了确认这个修复真的有效，我**先把修复回退掉跑了一遍测试，确认测试会红**，
> 再把修复装回去。还补了一条对照测试：普通历史消息压缩后确实对模型隐藏了 ——
> 证明压缩本身是生效的，不是测试写得太宽松。"

**可能的追问**：
- "为什么用 system 消息注入，不用 user？" → system 消息不会被用户看到，
  但模型一定看到。而且每轮重建，用户不需要在聊天里看到一堆进度快照。

## 6. "上下文装不下怎么办？"

**骨架**：

1. **派子智能体**（`delegate` 工具）——
   - 独立上下文：看不到你和用户的对话，所以 `task` 参数必须写全
   - 只回结论：中间过程**不进父上下文**
2. ⭐ **只读权限靠工具集本身保证，不靠提示词**：

> "子 agent 的只读工具集是**物理上**就没有写入工具和 `run_shell`，
> 不是靠 system prompt 说'你别改文件'。因为**模型不听提示词**。
> 比喻：不是给实习生贴张'请勿入内'的纸条，是压根不给他那间办公室的钥匙。"

3. **中断透传** —— 用户点"停止"，父 agent 和子 agent 必须一起停，
   否则子 agent 会继续烧 token。

**关键比喻**（值得说，很好懂）：

> "让实习生去查三个部门的档案：
> - **串行**：主 agent 自己查 A（桌上堆着 A 的全部资料）→ 查 B（A 的资料还堆着）→ 查 C → 桌子满了
> - **并行 + 子 agent**：三个实习生各查各的，各回一份**摘要报告**。主 agent 桌上只有 3 份报告
>
> 这就是子智能体的全部价值：**隔离上下文**。"

**可能的追问**：
- "子 agent 的结果怎么保证质量？" → 父 agent 只拿到一段文本结论，
  可以自己再验证（`read_file` 复核关键点）。子 agent 的价值是**省上下文**，不是**免验证**。
- "能递归派子 agent 吗？" → 不能，depth ≥ 1 直接报错。防止无限套娃烧钱。

## 7. 🔥 "成本怎么控？"

**骨架**（先给数据，再给手段）：

**数据**：最近一次全量评测**输入 token 占 95.4%**（1,379,691 / 66,322）。
原因很直接：**ReAct 循环每一步都要重发全部上下文**。

**三个手段**：

| 手段 | 省在哪 |
|---|---|
| **大输出外置** | 超大工具输出落盘，只回灌头尾预览。评测数据：输入 token 是输出的 20 倍，根源就在这 |
| **重复调用检测（四重校验）** | 参数一致 / 文件内容未变 / 原结果仍在上下文里 / 写后失效。四重都命中才提示"别重复了" |
| **渐进式技能加载** | 默认只给一行索引，模型要了才给正文 |

**再加上**：
- **消融实验**用来决定工具集要不要精简（摘 grep 成本降 25% 这个结论就是消融给的）
- **方差统计**排除噪声，别把随机波动当优化效果

**可能的追问**：
- "重复调用检测会不会误伤？" → 四重校验里最关键的是"原结果是否还在模型上下文里"——
  上下文被压缩掉了就不能说"你刚才已经读过了"，必须重读。
  这也是"重复检测第四重校验"要依赖 `refreshVisibleCallIds()` 的原因。

## 8. "失败了怎么恢复？"

**骨架**（三个层次的恢复）：

1. **协议层自愈** —— `historyRepair.ts` 在每次请求前扫一遍 messages，
   把孤儿 tool_call、顺序错乱、缺 id 的消息修成合法的。
   修法是**"显式告知未执行"**而不是"静默删除" ——
   删掉的话模型会以为它没被调用过，于是重复执行副作用。

2. **中断续跑** —— 用户点停止时：
   - 补齐**剩余全部** tool_call（不只是当前这一个），否则下一轮还是 400
   - checkpoint 记录已完成/未完成的工具，恢复时不重复副作用

3. **触顶强制收尾** —— 达到最大轮数时，不是甩一句"超限了"就走，
   而是发起一次**不带工具**的请求，让 LLM 把已经做的工作总结给用户。
   借鉴 nanobot 的 `_try_finalize_after_max_iterations`。

**⭐ 协议约束速查（能背出这张表就是加分）**：

| 非法序列 | 后果 |
|---|---|
| assistant 带 tool_calls，后面没有 tool 消息 | 400（永久） |
| assistant 带 N 个 tool_calls，只有 M<N 条 tool 消息 | 400 |
| tool 消息出现在对应 assistant 之前 | 400 |
| tool 消息没有 tool_call_id | 400 |
| assistant 与 tool 之间夹了 user 消息 | 400 |

## 9. "跟 Cline / Continue / Copilot 有什么区别？"

**⭐ 这题的原则是：绝不贬低对手。**

**正确答法**：

> "它们是**产品**，我的是**工程实践的载体** —— 这不是同一个赛道的比较。
> 我的差异化在**可测量性**：
>
> 我能给出每一道题的 **token 成本、工具调用轮数、回归失败数**。
> 而且我能做**消融实验**回答'这套题到底在测什么'——
> 摘掉 grep 之后 pass rate 变不变。
>
> Cline 有 pass/fail，但缺一个维度：
> **'这个失败是我的 agent 造成的，还是题目本来就难？'**
> 我的 baseline→after 三方比对就是为了区分这两件事。
>
> 另外我做的事里有几件是**产品型项目不会做的**：
> 比如给自己写架构守卫脚本、给评测题配人写的标准答案、
> 写脚本检查 VSIX 里有没有混进不该进的文件。
> 这些在产品里没有必要，但它们让'我的项目是可靠的'这件事**可被验证**。"

**⚠️ 不要说的话**：
"他们没有 CI"、"他们没测试"、"他们不支持 X" —— 一旦对方用过，立刻掉分。

## 10. "如果让你重做，你会怎么设计？"

**骨架**（三段）：

1. **已经做过的，别装成"将来会做"**：

> "有一条我其实已经做了：'如果代码量到 2 万行，我会把 ReAct 循环重构成 op 管线' ——
> **我现在就是这么写的**：`loop.ts` 从 1075 行降到 211 行，
> 9 个 Operation，每个只干一件事，能单独单测。
> 新增能力 = 往管线数组里加一项。"

2. **确实还会再进一步的两条**：

   - **Effect 式落盘**（goose 的做法）：
     每一步操作的状态落盘、崩溃后精确重放到任意一步。
     我现在的 checkpoint 是**文件级快照 + 工具级进度**，粒度没到"任意一步重放"。
   - **三层分离**（nanobot 的做法）：
     内核（工具契约）/ 编排（agent 循环）/ 治理（上下文、权限、成本）分成三个独立层。
     我现在治理层的逻辑还散在 operations/ 各个文件里。

3. **但我会克制**：

> "不过我不会追求完整复刻。这两个项目的目标环境跟我不一样 ——
> 它们跑在服务器上、要处理多用户和长时任务；
> 我这是个 VS Code 插件，跑在用户自己的机器上、任务是分钟级的。
> **过度的工程化对个人项目是负资产** ——
> 它会让真正值钱的东西（评测方法论、安全边界、上下文治理）没时间做。"

**这道题的隐藏考点**：看你**有没有判断力**，而不是看你会不会说"我想做 X"。

## 11. 🔥 "你看过什么工业级实现？"

**⭐ 这题是本项目最强的差异化点。核心是讲"我研究过并主动放弃了什么"。**

**参照对象**：

| 项目 | 我吸收了什么 |
|---|---|
| **goose**（Block，Rust） | Operation 契约 + 状态机（管线化主循环）、双可见性、OTel 字段名、上下文压缩阈值 0.7、工具名幻觉修复、未广告工具不执行 |
| **nanobot**（Python） | 工具四成员契约 + 元数据、渐进式技能加载、上下文治理的 compact_messages、触顶强制收尾、untrusted_content 片段 |
| **Claude Code** | TodoWrite 的三态设计（不是 goose 的字符串极简版） |

**⭐ 三个"主动放弃"，每个都要讲清理由**：

**① 拒绝 goose 的 LLM-as-judge 权限判定**

> "goose 用 LLM 判断'这次操作要不要问用户'。我明确拒绝了，理由写在代码注释里：
> 1. **慢** —— 每次工具调用多一次 LLM 往返
> 2. **烧钱** —— 一次任务几十次调用就是几十次额外请求
> 3. **判不准** —— LLM 判断'这危不危险'本身就能被注入
> 4. **不可预测** —— 同样的操作两次判断可能不一样，用户没法建立信任
>
> 我的做法是**静态元数据**：每个工具注册时声明有没有副作用，权限档位直接映射。
> 代价是它不认识'这次具体的参数危不危险'，
> 但对插件这个场景（用户自己的工作区、自己的 shell）够用了。"

**② 没有照抄 goose 的 31 项环境变量黑名单**

> "goose 有一个环境变量黑名单，防止 MCP 配置把 PATH 之类的东西注入进来。
> 我**读它是为了讲清楚为什么不能照抄** ——
> 它防的是 MCP 配置注入路径，**我根本没有 MCP**；
> 而我真正的注入来源是**仓库里的文件**。
> 照抄那份黑名单会把 PATH 删掉，直接弄瘫插件。
>
> 所以我做的是另一件事：**文件内容 ≠ 环境变量**的隔离 ——
> 工具输出统一包 `<untrusted_content>` 标记 + system prompt 全局规则。
> 而且我把信任边界打在**管线出口**而不是各工具内部 ——
> 这样 `run_shell` 的输出也被覆盖了（第一版只包 read_file/grep，是个真漏洞）。"

**③ 评测不用 LLM 打分**

> "断言必须是二值的，每题配人写的标准答案。LLM 给自己打分就是自我麻醉。"

**⭐ 加分点**：

> "顺便说个消融实验的发现：摘掉 grep 之后 agent 会用 `run_shell` 跑 **shell 版 grep**，
> **能力一点没少，只是绕了个弯**。所以消融一个 CLI 工具必须严格 ——
> 还得把 `run_shell` 一起摘掉。这是我自己的实验设计有漏洞，不是工具的锅。"

## 12. 🔥 "这个项目最大的技术难点是什么？"

**推荐答案：OpenAI 兼容协议下的 tool_call 配对约束 + 为什么压缩时必须把 assistant+tool 当整体保护。**

**骨架**：

> "最难的是 **OpenAI 兼容协议下的 tool_call 配对约束**。
>
> 规则是：assistant 声明了 N 个 tool_call，就必须紧跟 N 条 tool 消息，一一对应。
> 少一条 → provider 直接 400，而且**是永久 400** —— 对话卡死，重试没用。
>
> 两个触发场景：
> 1. AI 一次调多个工具，用户点「停止」→ 剩余 tool_call 永远没有回应
> 2. autocompact 压缩历史时，把 assistant 和它后面的 tool 消息**拆散**
>
> 第二个更严重：中断要用户主动点停止才触发，
> 而**压缩在任何长对话里必然触发**（阈值是上下文窗口 70%）。
>
> 解法有两层：
> - **压缩时分组保护** —— 遍历时把「assistant + 它后面所有 tool 消息」当成一个整体。
>   这里有个坑：**不能预先 `slice`** —— 预先切片正好会把一组拆开，
>   所以我用游标式遍历。
> - **请求前协议自愈** —— `historyRepair.ts` 扫一遍，把非法结构修成合法的。
>   修法是**"显式告知未执行"而不是"静默删除"** ——
>   删掉的话模型会以为它没被调用过，于是重复执行副作用。
>
> 为什么这个难点值得讲：**它不是'某个功能没写好'，它是'一个静默的、会杀死整个会话、
> 而且触发条件是必然发生'的 bug**。"

**⭐ 如果被追着问"还有别的难点吗"，可以补这两个**：

- **信任边界的位置**：第一版把提示注入防护打在各工具内部，
  结果 `run_shell` 的输出完全没防 —— 恶意 README 从命令输出直接进上下文。
  挪到管线出口才解决。**教训：安全边界应该收口，而不是分散。**
- **压缩与状态管理的耦合**：压缩会把消息标记为模型不可见，
  而状态如果存在消息里就会被一起压掉。
  所以待办状态必须独立于消息流（存 session），
  而且必须打 `pinned` 标记免于参与总结 —— 否则模型压缩一次后就"失忆"了。

## 附：三条通用答题纪律

1. **先给数字，再讲机制。**
   "输入 token 占 95.4%，因为 ReAct 每步重发全上下文" 比 "我会做上下文优化" 有力十倍。

2. **讲机制的时候要说"为什么不能用更简单的做法"。**
   这是区分"用过"和"懂"的分水岭。

3. **主动讲你的实验设计和实现踩过的坑。**
   面试官不怕你犯错，怕的是你不知道自己错在哪。
   **"我曾经把 Stop hook 的参数传错了，那个功能从来没跑起来过"** —— 这句话比十句"我实现了 hook"更值钱。
