## 第 1 部分：大模型基础

### 1. LLM（Large Language Model，大语言模型）

**通俗解释**：一个"读过全世界文本"的超级鹦鹉。它只会**接着往下写文字**，不会真的"理解"或"执行"。

**类比**：一个记忆力极好、但**只会照着你说的写**的实习生。你不告诉它做什么，它就不知道做什么。

**关键认知（很多人卡在这）**：
> **LLM 自己什么都做不了。** 它不能读文件、不能跑命令、不能上网。
> 它唯一能做的就是"输出一段文字"。
> **是"工具"给了它手脚。**

**你项目里**：`src/agent/provider.ts` —— 你把用户的话 + 工具清单发给它，它回你一段 JSON 说"我要调 read_file"。

---

### 2. Token（令牌）

**通俗解释**：模型处理文本的最小单位。**不是字，也不是词，是一个"片段"**。

**类比**：把一句话切成小积木。模型每次读和写都是按积木算的。

**大概换算**（你项目 `src/util/tokens.ts` 里的真实数据）：

| 内容 | 1 token ≈ |
|---|---|
| 纯英文 | 3.6 个字符 |
| 纯中文 | 1.4 个汉字 |
| 代码 | 2~3 个字符 |

**⚠️ 为什么这个换算重要**：同样 80000 字符，全英文只要 2 万 token，全中文要 6 万 token。
**估少了** → 提前压缩，白丢历史；**估多了** → 超上限被 API 拒绝，整轮崩。

**你项目里**：`src/util/tokens.ts` 的 `estimateTokens()`，按中英文分开算。

---

### 3. 上下文窗口（Context Window）

**通俗解释**：模型**一次能"看见"的文字总量上限**。

**类比**：模型的工作台面就那么大（64K token ≈ 一本 30 万字的中文书）。
**桌面放不下的东西，它根本不知道存在。**

**你项目里**：`src/util/tokens.ts` 的 `MODEL_CONTEXT_WINDOWS`：
`deepseek-chat` 64K、`MiniMax-M3` 128K、`gpt-4o` 128K。
`DEFAULT_CONTEXT_WINDOW = 64_000`（不认识就按保守的算）。

---

### 4. System Prompt（系统提示词）

**通俗解释**：每次请求里放在**最开头**的"给 AI 的岗位说明书"。

**类比**：新员工入职时发的那本《员工手册》。
不是用户说的话，是**系统**告诉它"你是谁、怎么干活、有哪些规矩"。

**⭐ 为什么它极其重要**：
> 你项目 `src/agent/context.ts` 的注释写得很准：
> *"system prompt 决定 agent 行为（写得对 = 行为正确 80%）"*
>
> 而且 **LLM 对开头的指令更敏感** —— 同样一句话放开头比放结尾有用。

**你项目里**：`src/agent/context.ts` 的 `buildSystemPrompt()`，拼 4 段：
身份 → 项目规则(AGENTS.md) → 技能 → 工作区信息。

---

### 5. Provider（模型供应商 / 提供方）

**通俗解释**：提供大模型 API 的公司或服务。

**类比**：不同的"发电厂"。你家里电器是通用的（OpenAI 兼容协议），
换发电厂只是换电源插头。

**你项目里**：`src/agent/provider.ts` 的 `PROVIDER_CONFIGS` 一张表，4 个：
minimax / deepseek / openai / ollama。
**加一家只改这张表，不动其他文件** —— 这是很好的设计。

---

### 6. BYOK（Bring Your Own Key，自带密钥）

**通俗解释**：插件不自己包 API key，用户填自己的。

**类比**：自己带米去食堂（食堂只负责做菜）。

**为什么重要**：
> **商业上**：不用付 API 成本，不用存用户密钥。
> **面试上**：这是"我知道产品该怎么落地"的信号。

**你项目里**：`mini-coder.setApiKey` 命令 + `src/config.ts`。
⚠️ 注意你的 `package.json` 里 provider 枚举**故意删掉了 anthropic**，
注释写得很清楚："之前它列在这里但代码里没有实现，选了会被静默丢弃"——
**这叫"不骗用户"，是加分项**。

---

### 7. Streaming（流式输出）

**通俗解释**：模型不是一次把答案全吐出来，而是**一个字一个字地往外蹦**。

**类比**：不是"快递送到你手上"，而是"快递实时轨迹一个一个刷新"。

**为什么 agent 特别需要**：agent 一轮要跑 20 多次 LLM 调用。
不流式的话，用户要盯着转圈 3 分钟；流式的话至少能看到"它在想什么"。

**你项目里**：`src/agent/provider.ts` 的 `stream()`，用 `ReadableStream` 逐块解析。

---

### 8. 幻觉（Hallucination）

**通俗解释**：模型**一本正经地编造**不存在的东西。

**类比**：实习生很自信地告诉你"这个 API 在 3.0 就被移除了"——**其实没有**。

**典型表现**：编出不存在的文件名、编出不存在的函数、编出一整段假代码。

**你项目里的对策**（三层）：
1. `context.ts` 的 system prompt 里写死规则：**"不要生造内容：read 不到就说不存在，不要瞎编"**
2. `delegate.ts` 的铁律 3：**子智能体必须如实报告，包括"我没找到"**
3. 评测题里专门有对抗题测这个

---

### 9. Temperature（温度）

**通俗解释**：控制模型输出的"随机性"。0 = 每次都一样，1 = 更有创意也更不靠谱。

**类比**：做饭时"放多少 spice"。放 0 = 每道菜味道一样；放高 = 可能惊艳也可能翻车。

**你项目里**：**你没做这个参数**（`provider.ts` 里没有 `temperature` 字段）。
这不一定是问题——**很多 coding agent 故意用低温度或默认温度**，追求稳定。
但如果面试被问"你怎么保证可复现"，这会是个好话题。

---

### 10. Prompt Caching（提示缓存）

**通俗解释**：如果你的 prompt 前缀**每次都一样**，模型服务端可以把它缓存起来，
后续请求**便宜且更快**。

**类比**：每次去同一家餐厅点同样的菜，厨房不用重新备料，出餐更快也更便宜。

**⭐ 这是个很值钱的认知**，goose 专门做了优化：
- `prompt_manager.rs:117-118`：**工具顺序必须稳定**（排序固定 → 缓存命中）
- `prompt_manager.rs:188-190`：**时间戳截断到小时**（不要写精确到秒）

> **你项目里**：⚠️ **没做**。你的 `registry.schemas` 是 `Map` 遍历，
> 顺序稳定（JS 的 Map 保持插入顺序），这点是对的 ✅。
> 但 system prompt 里如果有动态时间戳，就要小心。

## 第 2 部分：Agent 核心

### 11. Agent（智能体）

**通俗解释**：**LLM + 工具 + 循环** 三样东西组装起来的东西。

**类比**：
- LLM 只有一个 = 一个**只能动嘴的**人
- 加上工具 = 有了**手脚**
- 加上循环 = 有了**"想 → 做 → 看结果 → 再想"**的自主性

**关键分界线**：
> **LLM 是一次性问答，Agent 是能自己往下推进的。**
> 判断标准：**它能不能自己决定下一步做什么。**

**你项目里**：`src/agent/loop.ts` 的 `AgentLoop` 就是这个"循环"。

---

### 12. ⭐ ReAct（Reasoning + Acting，推理+行动）

**通俗解释**：让模型**交替**做两件事——先想，再做，然后看着做的结果再想。

**类比**：不是"你问一句我答一句"，而是**"我去看一眼 → 我发现了什么 → 我再去看一眼"**。

**举个你项目里的真实例子**（评测题 01 的 toolTrace）：
```
1. list_dir    → 看到目录里有 username.js
2. read_file   → 读到代码，发现只判了长度
3. glob        → 找 check.js，没找到
4. apply_patch → 改代码，加了类型检查
5. run_shell   → 跑测试，"ALL PASS"
6. 最终回答    → 汇报改了什么、为什么这么改
```

**注意第 3 步**：模型去找了测试文件，**没找到**，于是自己决定"那我手写个 node -e 断言来测"。
**这就是 agent 和"照着步骤执行"的分界线** —— 它会自己补上缺失的环节。

**你项目里**：`src/agent/loop.ts` 顶部注释写得很清楚：
*"LLM 是一个只能看说明书、不能动手的助手"*

---

### 13. ⭐ Agent Loop（智能体循环）

**通俗解释**：**驱动 agent 不断"想→做"的那个 while 循环**。

**类比**：餐厅后厨的出菜循环：接单 → 做 → 尝味 → 调整 → 上菜。

**你项目里**（这里有个**你做得特别好的地方**）：
```typescript
// src/agent/loop.ts:200-208  ← 改造前这个循环是 1075 行，现在只有 9 行
while (true) {
  for (const op of this.pipeline) {
    const result = await op.run(ctx);
    if (result.status === 'yielded') {
      return result.output;      // 任务结束
    }
  }
  ctx.iteration++;
}
```
> **你把它拆成了 9 个 Operation**（abort / max_iterations / user_prompt_submit /
> steer_inject / todo_inject / context_guard / inference / tool_execution / stop_hook）。
> **这是从"一坨代码"变成"一条流水线"的典型改造，面试必讲。**
>
> ⚠️ 常见口误：把 `src/agent/operations/` 的**文件数**（11 个）说成 Operation 数。
> 那个目录里只有 **9 个**是 Operation，另外两个是 `types.ts`（契约）和 `index.ts`（装配）。
> 真相源：`src/agent/operations/index.ts` 的 `ALL_OPERATION_NAMES`（9 项）。

---

### 14. ⭐ Tool Call / Function Calling（工具调用）

**通俗解释**：模型输出的一段**结构化 JSON**，说"我要用哪个工具、参数是什么"。

**类比**：助理填写的借阅单 —— 上面写着"书名、借期、姓名"，图书馆照单去取。

**⚠️ 关键误解澄清**：
> **模型不执行工具。它只是"填了一张单子"。**
> 真正执行的是**你的代码**（`registry.execute()`）。
> 这就是为什么"工具名写错"会失败——单子上写错书名，图书馆找不到。

**你项目里**：`src/agent/tools/registry.ts` 的 `execute()`。

---

### 15. ⭐ Tool Schema（工具说明书）

**通俗解释**：每个工具的"说明书"，告诉模型**这个工具干什么、需要什么参数**。

**类比**：菜单。每道菜有名字、描述、价格（参数规格）。

**⚠️ 这是模型选工具的唯一依据**：
> 模型看不到你的代码，**它只能看到这份说明书**。
> 说明书写得含糊 → 模型选错工具 → 浪费一整轮 LLM 调用。

**你项目里**：`src/agent/tools/base.ts` 的 `parameters` 字段 + `toOpenAISchema()`。

---

### 16. Operation（操作）

**通俗解释**：**Agent 循环里的一个步骤**。每个 Operation 只干一件事。

**类比**：流水线上的工位 —— 上料、加工、质检、装箱，各管一段。

**三个状态**（你项目 `src/agent/operations/types.ts` 定义的）：

| 状态 | 含义 | 类比 |
|---|---|---|
| `not_applicable` | 这轮不适用，跳过 | 工位发现这批货不需要质检，直接跳过 |
| `applied` | 做了事，继续往下 | 正常完成本工位 |
| `yielded` | 任务结束 | 装箱完成，出厂 |

**你项目里**：`src/agent/operations/` 下 11 个文件。

---

### 17. 并行 vs 串行（工具执行）

**通俗解释**：
- **并行** = 同时干（同时读 3 个文件）
- **串行** = 一个接一个（改文件必须一个一个来）

**⚠️ 你项目里的关键设计**（`src/agent/tools/partition.ts`）：
> **只读工具并行，写工具串行。**
>
> 为什么写工具不能并行：
> 1. 两个 patch 改同一个文件会互相覆盖
> 2. 两个审批弹窗同时弹出来，用户懵了
> 3. 两个 shell 命令的副作用顺序不可控

**⭐ 面试考点**：goose 的核心循环是**严格串行**的（`tool.rs:362` 是 `for ... await`），
**你的实现比它更进一步** —— 这可以讲。

---

### 18. Max Iterations（最大轮数）

**通俗解释**：agent 最多能转多少圈。

**类比**：给员工设"最多加班到 10 点"。

**为什么必须有**：LLM 有可能陷入死循环（改一版→测试还挂→再改一版→再挂…），
**没有上限就是无限烧钱**。

**你项目里**：`src/agent/limits.ts` 的 `MAX_ITERATIONS = 30`，
而且**触顶不是甩一句"超限了"就走**，而是发起一次**不带工具**的请求，
让模型把已完成的工作总结给用户。**这个细节很加分。**

---

### 19. ⭐ 多步任务状态管理（Todo / 计划）

**通俗解释**：任务复杂时，agent 需要**记着自己走到第几步了**。

**类比**：装修要分 8 步，墙纸上贴着 checklist，
每完成一步打个勾。**不然工人刷着刷着就忘了刷到哪了。**

**⭐ 为什么这在你的项目里特别重要**：
> 因为**你的上下文会被自动压缩，历史对话会被压掉**。
> 如果待办只存在对话历史里，压缩之后就跟着没了 →
> agent "忘了"自己走到第几步 → 重复做或者从头再来。
>
> **所以待办必须存在 session 文件里，和对话历史分开存。**
> 这是你 `src/session/store.ts` 里 `SessionMeta.todos` 的设计原因。

---

### 20. ⭐ Sub-agent / Delegate（子智能体）

**通俗解释**：主 agent 派一个"临时工"去查东西，**只带回结论**。

**类比**：主 agent 的桌子放得下 20 页卷宗，但活儿可能有 300 页。
派三个实习生各查各的，**主 agent 桌上只有 3 份报告**。

**这就是子智能体的全部价值：隔离上下文。**

**你项目里的三条铁律**（`src/agent/tools/delegate.ts` 顶部注释，很漂亮）：
1. **子 agent 绝不能有写权限** —— 靠**工具集本身**保证，不是靠提示词
   （"模型不听提示词，尤其是被诱导的时候"）
2. **不能递归套娃**（a 派 b，b 派 c，无限烧钱）
3. **必须如实报告，包括"我没找到"**（否则父 agent 基于幻觉做决策）

---

### 21. Steering（插话 / 实时干预）

**通俗解释**：agent 正在干活，用户中途插一句"哎那句改一下"，它听到但**不推倒重来**。

**类比**：秘书正在写稿，老板推门说"第三段换个说法"，
秘书**改那一句**，不会把整篇重写。

**你项目里**：`src/agent/steering.ts` 的队列 + `operations/steerInject.ts`。
实现上很巧——**队列和面板共享同一个数组引用**，所以面板 push 进来的话，Operation 直接能取到。

---

### 22. Skills（技能包）

**通俗解释**：一个文件夹里放一份 Markdown，说明"遇到这类任务该怎么做"。

**类比**：员工手册里的"标准作业流程（SOP）"。

**⭐ 核心设计 = 渐进式披露（progressive disclosure）**：
> **不在 prompt 里塞全文，只塞索引。**
> 需要哪份才加载哪份的正文。
>
> 比喻：**目录贴在墙上，需要哪一页再翻。**（而不是把整本手册背下来）

**你项目里**：`src/skills/loader.ts` + `skills/` 下 3 个内置技能
（code-review / debug-workflow / test-writing）。
**借鉴 nanobot 的 `skills.py:180-241`**（`build_skills_summary`）。

## 第 3 部分：上下文工程

### 23. ⭐ 上下文工程（Context Engineering）

**通俗解释**：**决定"每一轮到底给模型看什么"的艺术**。

**类比**：老师批改作业时 decides 给你看哪几页参考书 —— 看太多看不完，看太少答不出。

**2026 年的核心认知**：
> **Prompt Engineering 已经过时了。**
> 提示词只是"第一段上下文"。
> 真正决定 agent 表现的是：历史怎么管、工具怎么描述、
> 状态怎么存、什么该压缩、什么该 pin 住。

**你项目里**：你有一整个 `operations/contextGuard.ts` + `visibility.ts` +
`trust.ts` + `toolOutputStore.ts` 在做这件事。
**这是你项目最值钱的部分之一。**

---

### 24. 上下文压缩 / Compaction

**通俗解释**：对话太长放不下了，就**把老内容总结成一段话**，腾地方。

**类比**：会议开了一整天，快撑不住了 →
主持人说"前面我们讨论了 A、B、C 三个方案，最后倾向 B，散会"。

**你项目里**：`src/agent/operations/contextGuard.ts`。
触发阈值是**上下文窗口的 70%**。

---

### 25. ⭐ 双可见性（Double Visibility）

**通俗解释**：**模型看到的对话 ≠ 用户看到的对话**。

**类比**：同一份卷宗，桌上给助手的是**摘要**，档案柜里存**全文**。

**你项目里的做法**：
```typescript
// src/agent/visibility.ts
// agentVisible=false → 这条消息【不再发给模型】，但仍保留在文件里，
//                      用户在面板里仍能滚动查看（灰显状态）
```

**⭐ 为什么这个设计值得讲**：
> 1. 用户想回看"agent 当时到底看到了什么" —— 物理删除就永远找不回来了
> 2. **压缩是可逆的**（取消标记就回来了），物理删除不可逆
> 3. 借鉴 goose 的 `agent_visible_content` / `user_visible_content`

### 26. Pinned（钉住的消息）

## 第 5 部分：工具与权限

### 39. ⭐ 工具元数据（Tool Meta）

**通俗解释**：每个工具**在注册时就声明好**"我会不会改东西、能不能并发"。

**类比**：公司给每个岗位标一个**风险等级标签**。

**你项目里的四个字段**（`src/agent/tools/meta.ts`）：

| 字段 | 意思 | 后果 |
|---|---|---|
| `readOnly` | 只读吗 | 只读 → 权限档位自动放行 + 允许并行 |
| `destructive` | 破坏性吗 | 破坏性 → 强制存 checkpoint |
| `concurrentSafe` | 能并发吗 | 写操作一律 false |
| `kind` | 属于哪类 | `read` / `write` / `exec` 三选一 |

**⚠️ `kind` 为什么单独一个字段**（注释写得很清楚）：
> `write_file` 和 `run_shell` 的 `readOnly` 都是 false、`destructive` 都是 true，
> 只靠这两个字段区分不出「改文件」和「执行任意命令」。
> **但这两者在权限上必须是两件事**——
> 改文件改了能撤回，跑命令可能 rm -rf、可能推远端，撤不回来。

### 41. ⭐ LLM-as-Judge（用 LLM 判断权限）

**通俗解释**：每次工具调用前，**再调一次 LLM 问"这操作危不危险"**。

## 第 10 部分：行业通用名词（你可能还不会的）

> 这部分不在你项目里，但**求职面试会问到**，而且和你 wxu 项目的 RAG 有关。

### 93. ⭐ RAG（Retrieval-Augmented Generation，检索增强生成）

**通俗解释**：**回答之前先去资料库里查**，把查到的内容塞给模型，让它照着答。

**类比**：开卷考试。允许带资料，但资料得自己找。

**为什么需要**：模型不知道你公司的私有文档，RAG 让它"现查现用"。

**你 wxu 项目**：核心。

---

### 94. ⭐ Embedding（嵌入向量）

**通俗解释**：**把一段文字变成一串数字**，让"意思相近的文字"在数字空间里也相近。

**类比**：给每本书一个**图书馆坐标**。
"找讲数据库的书" → 直接去数据库那个区域翻，不用逐本看。

**你 wxu 项目**：bge-m3，1024 维。

---

### 95. ⭐ 向量数据库（Vector DB）

**通俗解释**：**专门存 embedding、并且支持"找最像的几个"的数据库**。

**类比**：不是按书名排的图书馆，是**按内容相似度排的图书馆**。

**你 wxu 项目**：29376 chunks。

---

### 96. Chunk（文本块）

**通俗解释**：**把长文档切成小段**再存进向量库。

**类比**：把一本书拆成一叠卡片，每张卡片能单独抽出来。

**⚠️ chunk_size 是关键参数**：切太大 → 噪声多、token 贵；切太小 → 上下文断了。

---

### 97. ⭐ Recall@k（召回率）

**通俗解释**：**正确的资料有没有被检索出来**（前 k 个结果里）。

**类比**：老师出题后翻资料，**翻 10 页内有没有翻到那道题的出处**。

**RAG 的第一道关卡**：检索不到，后面生成得再好也没用。

---

### 98. ⭐ Reranker（重排序模型）

**通俗解释**：检索先粗排 100 条，再用**一个更准但更慢的模型**精排前 10 条。

**类比**：先从全图书馆找出 100 本可能相关的，
再请一个懂行的 librarian 精挑出最该看的那 10 本。

**为什么需要**：向量检索快但粗，rerank 慢但准。

---

### 99. ⭐ RRF（Reciprocal Rank Fusion，倒数排名融合）

**通俗解释**：**把多路检索的排名合并**成一个排名。

**类比**：三个评委分别给 10 本书打分排名，
不直接比总分（不同评委尺度不同），而是**看每本书在每个名单里排第几**，
排得都靠前 book 得分高。

**公式**：`score = Σ 1/(k + rank_i)`，k 通常取 60。

**你 wxu 项目**：关键词检索 + 向量检索融合。

---

### 100. HyDE（假设性文档嵌入）

**通俗解释**：**先让模型"幻想"一个答案**，用这个假答案去检索。

**类比**：你不知道答案时，**先写个大概的草稿**，
拿草稿去图书馆查，比拿"关于XX的问题"去查准得多。

**因为**：问题和答案的语义距离，比问题和问题之间的小。

---

### 101. ⭐ 幻觉率（Hallucination Rate）

**通俗解释**：**编造内容占回答的比例**。

**你 wxu 项目**：RAG 场景下最关键的指标 —— 模型很容易"根据知识编答案"，
而不是"根据检索到的内容答"。

---

### 102. 文档级 / 块级 / 片段级切分

**通俗解释**：检索粒度的选择。

**类比**：图书馆是**整本书借**、还是**按章节复印**、还是**按段落复印**。

---

### 103. ⭐ Query Rewrite（查询改写）

**通俗解释**：**把用户的原始问题改写成更好检索的形式**。

**类比**：用户问"它怎么用"，
系统判断出"它"是指向量库，改写成"向量库 怎么用"。

---

### 104. HyDE + Query Rewrite + Rerank 的组合

**通俗解释**：RAG 的**三段式标准流程**：
```
用户问题
  → 改写（让它更适合检索）
  → HyDE（造个假答案当检索词）
  → 混合检索（关键词 + 向量）
  → RRF 融合
  → Rerank 精排
  → 塞给模型生成答案
```

---

### 105. ⭐ Agentic RAG

**通俗解释**：**RAG 不再是一次性检索**，而是 agent 自己决定"查几次、查什么、要不要再查"。

**类比**：普通 RAG 是"你去图书馆查一次，抄一段回来写答案"；
Agentic RAG 是"**你是个调研员**，自己去图书馆，翻到哪儿查到哪儿，
发现资料不够就再去别的书架翻"。

**⭐ 这是 2025-2026 RAG 领域最热的方向。**
**你 wxu 项目已经有多模态 + agent 化，可以往这个方向讲。**

---

### 106. GraphRAG（图检索增强）

**通俗解释**：**先建实体关系图**，再在图上检索。

**类比**：普通 RAG 是"按关键词找段落"；
GraphRAG 是"先看**人物关系图**，找出谁跟谁有关，再去读相关段落"。

**适合**：问"X 和 Y 是什么关系"这类问题。

---

### 107. ⭐ Multi-Agent（多智能体）

**通俗解释**：**多个 agent 分工协作**。

**类比**：一个项目组 —— 产品经理、程序员、测试各管一段。

**⚠️ 但**：**多 agent 不一定比单 agent 好**。
多 agent 会带来：通信开销、协调难题、错误放大。
**很多"多 agent 框架"其实不如一个好的单 agent + 好工具。**

**你项目里**：你有 `delegate`（子智能体），但**不是多 agent 框架**——
是"主 agent 派临时工去查东西"。**这个区别要讲清楚。**

### 111. Tool Use vs. Function Calling vs. MCP

| 名字 | 是什么 |
|---|---|
| **Tool Use** | 大类说法："让模型用工具" |
| **Function Calling** | OpenAI 的具体协议格式 |
| **MCP** | **跨厂商**的接工具标准（Anthropic 发起，现在的事实标准） |

**类比**：
- Function Calling = 厂商自己定的插头
- **MCP = 行业统一的插头规格**（你项目要做这个）

### 112. MCP（Model Context Protocol）

**通俗解释**：**让 agent 用统一方式接入外部工具/数据源的标准**。

**类比**：**插座标准**。以前每个电器厂家自己设计插头，
现在统一了，一个插座适配所有电器。

**三种传输**：
| 传输 | 怎么传 | 适合 |
|---|---|---|
| **stdio** | 管道（启动一个子进程） | 本地工具（你项目要做的） |
| HTTP | 网络请求 | 远程服务 |
| SSE | 服务器推送 | 远程 + 流式 |

**你项目里**：❌ 还没做，是路线图 Phase 10.1。

**你项目里**：❌ 没有。**你也不该做** —— 那是研究课题，不是校招项目。

### 115. ⭐ 量化（Quantization）

**通俗解释**：**把模型参数从 16 位压到 4 位**，体积小 4 倍、速度快、但精度略降。

**类比**：把高清原图转成压缩图。

**你项目里**：`ollama` provider 意味着你能跑**本地小模型**
（比如 `qwen2.5-coder:7b`，你的 `MODEL_CONTEXT_WINDOWS` 里有它）。
这就是量化的成果。

### 116. ⭐ MoE（Mixture of Experts，专家混合）

**通俗解释**：**模型里有很多"专家"子网络，每次只激活其中几个**。

**类比**：医院有 20 个专科医生，
你看什么病就派哪个科，不会把 20 个医生全叫来。

**效果**：**参数量很大，但每次推理只用到一小部分** → 又大又快。

---

### 117. ⭐ KV Cache（键值缓存）

**通俗解释**：**模型生成时，前面已经算过的部分直接复用，不重算**。

**类比**：翻译长句子时，翻到第 5 句不会把前 4 句重翻一遍。

**⭐ 和 Prompt Caching 的区别**：
- **KV Cache**：模型内部，生成第 2 个字时复用前面的计算
- **Prompt Caching**：服务端，你重复发同样的前缀，它直接返回缓存

### 120. ⭐ 工具调用的"广告"机制

**通俗解释**：**每轮只告诉模型"你现在能用哪些工具"**。

**类比**：会议开始时念一遍与会者名单，**念过的人才能发言**。

### 121. 提示缓存的命中条件

### 122. 成本优化：为什么"输入"比"输出"贵

**通俗解释**：ReAct 循环**每一步都要重发全部历史**。
跑 20 步 = 20 次完整历史。

**所以**：省 token 的关键是
- **压缩上下文**（少发历史）
- **大输出外置**（少发工具输出）
- **子智能体隔离**（中间过程不回主上下文）

**你项目里**：三个全做了。**这就是为什么你的成本能压下来。**

### 124. 幂等性（Idempotency）

**通俗解释**：**同一个操作做 1 次和做 10 次，结果一样**。

**类比**：按电梯按钮，按一次和按十次都是"启动一次"。

**你项目里**：

### 125. ⭐ 熔断（Circuit Breaker）

**通俗解释**：**某个服务连续出错，就先别再打它了**，等一会儿再说。

**类比**：保险丝跳闸了，先断开电源，别让整栋楼都烧了。

**注释里写的理由**："BYOK 产品的生死线"——
用户填了自己的 key，provider 一挂，产品就废了。
