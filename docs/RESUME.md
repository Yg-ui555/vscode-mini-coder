## 一、项目名与一句话

**项目名**

> Mini-Coder —— 带回归检测的自评测 AI 编程助手（VS Code 插件，TypeScript，MIT 开源）

**一句话**（选一句）

- A 版（突出工程化）：面向中文开发者的 VS Code AI 编程助手。核心不是"能对话"，而是**能证明自己是对的**—— 内置带回归检测的评测体系，把 AI 编程助手最典型的失败模式（改对目标、弄坏别处）变成可测量、可回归的工程指标。
- B 版（突出 agent 岗能力）：自研 ReAct Agent 运行时 + 30 题三档难度评测集。做了管线化主循环、上下文治理、协议层自愈、子智能体上下文隔离、提示注入防线，能给出每道题的 token 成本 / 工具调用轮数 / 回归失败数。

### 关于 pass rate 100% 这件事，面试要主动讲

**别藏，也别吹。** 正确的说法是：

> "我这批题在 2026-10-24 跑出来是 100% 全过。但这恰恰说明**尺子坏了**——
> 题目太简单，测不出差别。所以我做了两件事：一是**加规模型题目**（41-44，40-60 个文件的合成代码库，

这段话比"我的评测集 100% 通过"值钱十倍，因为它是**方法论**而不是**战绩**。

## 四、STAR 故事（每个 2-3 分钟，面试口头讲）

### 故事 1：压缩把待办状态压没了（⭐ 最推荐）

**S**：给 agent 加了待办清单功能（多步任务的状态管理），存在 session 里，每轮重建注入上下文。

**T**：验收标准是"上下文压缩之后待办还在"。

**A**：写完发现压缩逻辑会把所有"纯对话消息"送去总结并标记为模型不可见——
待办状态是 `role: 'system'` 的消息，正好落在这个分类里。
更麻烦的是 `filterForModel` 会**永久**过滤掉这类消息，
所以压缩一次之后，模型就再也看不到待办状态了，多步任务必然从头再来。

**R**：加了一个通用机制 —— 消息打 `pinned: true` 标记就永不参与压缩。
待办状态和用户插话都打上这个标记。为了确认这个修复真的有效，
我**先把修复回退掉跑了一遍测试，确认测试会红**，再把修复装回去。
另外补了一条对照测试：普通历史消息压缩后确实对模型隐藏了 ——
证明压缩本身是生效的，不是测试写得太宽松。

**这个故事为什么值得讲**：它同时展示了三件事 —— 对协议/上下文机制的深入理解、
"先验证测试有效再相信它"的工程纪律、以及"用通用机制而不是特例补丁"的设计判断。

### 故事 2：Stop hook 从来没跑起来过（协议细节 + 排查能力）

**S**：给 agent 加了 hook 机制，四个生命周期点，用户可以在 `hooks.json` 里配自定义脚本。
其中 Stop hook 的定位是"测试没过不许收工"。

**T**：用户反馈说 Stop hook 配了没反应。

**A**：查下来是调用签名对不上 —— hook 执行器的签名是 `runStop(response, cwd, iteration)`，
而主循环传的是 `runStop(response, iteration)`，
**轮次号被当成工作区路径传给了 `spawn`**，Node 直接抛 `ERR_INVALID_ARG_TYPE`。
换句话说，这个功能上线以来一次都没成功运行过。
另外两处也有问题：`runPreToolUse` / `runPostToolUse` 漏传 cwd（undefined，
导致命令继承的是扩展宿主目录而不是用户工作区），`iteration` 从未传给任何 hook。

**R**：三处全部修正。教训记在代码注释里：
**"一个没人验证过的功能，等于不存在"**——所以现在 hook 相关路径有专门的回归测试。

### 故事 3：测量工具的 bug 比被测对象更可怕

**S**：自研评测框架，每题跑 baseline → agent → after 三方比对。

**T**：第二批评测跑出 2 处"回归"失败。

**A**：逐条核对发现**全是断言写错了** —— agent 调 `record_note` 往 `.notes/` 写错题本，
那是产品的正常功能，而我的断言写着"这个目录一个字节都不能动"。

**R**：从那之后加了**人写的标准答案**（oracle）：每道题配一份 `oracles/*.solution.js`，
`npm run eval:solvable` 执行它之后要求全部 case 一个不挂。
**目的不是"检查 agent"，是"检查题目本身是不是废题"。**
因为废题会以"满分"的形式混进评测集 —— agent 做对了却拿不到分，
你看到 pass rate 掉了，第一个反应会是"模型变差了"，去调提示词、换模型，
全在错误的方向使劲，真正的 bug 反倒被藏了起来。

**这个故事为什么值得讲**：它体现的是"**测量工具本身的质量，和被测对象一样重要**"这个工程判断。
面试官问"你怎么知道你的 agent 是对的"，这就是答案。

### 故事 4：消融实验揭穿了消融实验自己的漏洞

**S**：做工具消融实验 —— 把某个工具从给 LLM 的 schema 里摘掉，看题还过不过。
用来回答"这套题到底在测什么"。

**T**：第一轮消融：摘掉 `grep`，pass rate 依然 100%，成本还降了 25%。

**A**：看轨迹发现 agent 转头就用 `run_shell` 跑了 **shell 版 grep**：

```
grep -rn "readConfig\|loadConfig\|printConfig\|bootstrap\|processTask" src/ test/
```

**能力一点没少，只是绕了个弯。** 所以"消融一个 CLI 工具"必须严格：还得把 `run_shell` 一起摘掉。

**R**：改成严格消融（摘 grep + run_shell）。结果更意外：
**连一条命令都跑不了，28/28 依然全过** —— 纯靠读代码推理就做对了。
这说明那批题考的是"代码理解 + 推理"，不是"工具使用"。
于是我按这个结论去加**规模型题目**（41-44），让"能不能搜索"变成真正的瓶颈。

**这个故事为什么值得讲**：它证明你会**质疑自己的实验设计**，而不只是跑出数字。
而且顺带证明了"评测轨迹必须记录工具参数"——之前轨迹里 `args` 恒为空对象，
只能看到"调了 35 次 run_shell"，分不清跑的是 `ls` 还是 `grep`，这两种结论完全相反。

### 故事 5：CSS 变量写在 `:root` 上，亮色主题整版垮掉（⭐ 界面岗 / 工程深度）

**S**：给插件做界面重做，同时支持深色和亮色两套主题。

**T**：验收标准是"亮色主题下文字、边框、卡片全部正常"。

**A**：切到亮色主题，整版垮掉 —— 正文变成浅灰几乎看不见、卡片变成黑块。
但**控制台一条报错都没有**，DOM 结构对、类名对、变量名也对。
根因在 CSS 变量解析机制：`var()` 是在**声明它的那一层**完成替换的。
我把设计令牌声明在 `:root` 上，而主题变量（`vscode-light` / `vscode-dark` 类）挂在 `body` 上——
两者不在同一层，整条链路就静默错位了。

**R**：把令牌层从 `:root` 挪到 `body`，让"声明层"和"主题变量层"落在同一层，亮色立刻正确。
另外把这条写成了设计规范进了代码注释：**主题令牌必须声明在与主题变量同一层**。

**这个故事为什么值得讲**：它展示的是**静默失败的定位能力**——
没有报错、没有堆栈、没有红字，只有"看起来不对"。
很多人遇到这种会先去调颜色值，而正确的动作是去查机制。

### 故事 6：并行工具的结果挂错了工具（协议理解）

**S**：agent 支持并行调用只读工具（read_file / grep / glob / list_dir 一起发）。

**T**：验收标准是"每个工具调用旁边显示的是它自己那次的结果"。

**A**：并行 4 个工具时，前 3 个永远显示不出结果，第 4 个的结果被显示了 4 次。
翻协议才发现：扩展侧对并行是**先发 N 条 tool_call、再按序发 N 条 tool_result**
（`toolExecution.ts`），而前端把结果一律挂到"最后一条工具调用"上——
协议本身是按序的，前端却按"最后一条"配对。

**R**：改成**同名 FIFO**（按工具名找到最早那个还没结果的调用填上）。
顺手把前端的消息模型从"合并多条 assistant 消息"改成**扁平事件时间线**，
顺序天然正确，不再靠启发式推断轮次。

**这个故事为什么值得讲**：它说明**"协议是对的"不等于"实现是对的"**，
也说明"先读协议再改代码"比"改到看起来对"重要得多。

## 五、面试官可能问"这个数字怎么来的"（准备好出处）

| 问法 | 你要能立刻说出的出处 |

## 六、可能被问到但**你不会**的东西（提前想好怎么答）

**诚实原则：不知道就说不知道，但要说清楚你会怎么查。**

| 问题 | 建议答法 |
|---|---|
| "接入 MCP 了吗？" | 没有。评估过，判断是重复建设（VS Code 用户已有 Copilot 的 MCP 生态），而且它会引入"外部工具的输出是几级不可信"这个问题。**我的信任边界目前只处理"本地工作区的文件内容"这一档。** |
| "沙箱隔离呢？" | 插件跑在用户自己的机器、用户自己的 shell 里，信任边界跟服务器端 agent 完全不同。我的做法是**写前审批 + checkpoint + diff 预览 + 一键回滚**，不是隔离。 |
| "完整 provider 矩阵？" | 4 个主流。加 provider 只改 `PROVIDER_CONFIGS` 一张表 —— 这是刻意的设计取舍，不是遗漏。 |
| "支持多 agent 协作吗？" | 只有一层：`delegate` 派子智能体（独立上下文 + 只读工具集）。没有做多 agent 协商，因为**没有真实场景证明需要**。 |
| "代码覆盖率多少？" | 实测值（见 `npm run test:coverage`），CI 里设了 threshold 防回退。**报数字前先跑一遍，别背旧数。** |
| "为什么不用 Effect 那种持久化状态机？" | 研究过 goose 的实现。它的每步落盘 + 重载会话在"进程崩溃要精确恢复"场景更彻底。我选了 checkpoint 快照 + 协议自愈，复杂度低一个量级。**这是"够用就停"的判断，不是不知道有更好的。** |

## 七、写简历时的三条纪律

1. **每个技术点后面挂一个数字或一个可验证的机制。**
   "支持多 agent" 是词；"子 agent 只读工具集物理约束 + 中间过程不进父上下文 + 主上下文增量 < 500 token" 是证据。

2. **写"为什么"，不写"是什么"。**
   面试官问的是"你为什么这么设计"，不是"你用了什么框架"。
   "接入 X 框架"没有信息量；"研究过 X 然后判断在我们的场景下不适用，理由是……"有。

3. **主动讲你放弃的东西。**
   这是本项目最强的差异化：**不是功能数量，是"研究过工业方案并主动放弃了什么"**。
   例子：
   - 拒绝 goose 的 LLM-as-judge 权限判定（慢、烧钱、判不准、可被注入）
   - 没有照抄 goose 的 31 项环境变量黑名单（它防的是 MCP 配置注入路径，本项目无 MCP；照抄会删掉 PATH 弄瘫插件）
   - 没有做完整 provider 矩阵（一张表够用）
   - 评测不用 LLM 打分（自己给自己打分是自我麻醉）

   每一个"不做什么"背后都有理由，**这比"做了什么"更能证明你懂**。
