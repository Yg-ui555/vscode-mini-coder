# 消融实验（ablation）

> 目的：回答一个比"pass rate 高不高"更重要的问题 ——
> **这套题到底在测什么？**
>
> 2026-10-25 · deepseek-chat · 题目 31-35（5 道 Phase 2 新题）

---

## 1. 为什么要做消融

补完 5 道难题之后，任务级 pass rate **仍然是 100%**（28/28 目标 case 修好，0 回归）。

单看这个数字什么都证明不了 —— 可能是：
- (a) 题目太简单，送分
- (b) 当前 agent 确实够强

**消融实验能区分这两种情况**：把某个工具从 agent 的工具清单里摘掉，
看题还过不过。过不了 → 这题确实在测那个工具对应的能力；照样过 → 这题测的是别的东西。

```bash
npm run eval -- --ablate grep              # 摘掉 grep
npm run eval -- --ablate grep,run_shell    # 严格消融（见下面第 3 节）
```

被摘掉的工具**不会出现在给 LLM 的 schema 里** —— 它连"有这个工具"都不知道。

---

## 2. 三组结果

| 配置 | 可用工具 | Pass Rate | 目标 case 修好 | token | 成本 | 轮数合计 |
|---|---|---|---|---|---|---|
| **全量** | 9 个工具 | 100% (5/5) | 28/28 | 719,924 | ¥1.5734 | 79 |
| **摘 grep** | 8 个（无 grep） | 100% (5/5) | 28/28 | 529,028 | ¥1.1795 | 71 |
| **摘 grep + run_shell** | 7 个（只能读和改） | 100% (5/5) | 28/28 | 603,755 | ¥1.3197 | 80 |

（同配置重复跑一次的波动：¥1.145 ↔ ¥1.1795，约 3% —— 这是单次运行的噪声量级，
**所以下面所有结论只按"方向"读，不按小数点读**。）

### 结论一：这三道题不测"会不会用 grep"

摘掉 grep，agent 照样 28/28 全过。

轨迹显示它换成了 `list_dir` + `glob` + `read_file` 把整个沙箱读了一遍 ——
**题目的代码库只有 5-9 个文件，根本不需要搜索能力**，
"把影响面找全"在小仓库里靠通读就能做到。

### 结论二：⭐ 消融本身有个漏洞：`run_shell` 是后门

第一轮消融（只摘 grep）结束后，轨迹里出现了这条命令：

```
grep -rn "readConfig\|loadConfig\|printConfig\|bootstrap\|processTask" src/ test/
```

—— agent 转头就用 `run_shell` 跑了 **shell 版 grep**。

**能力一点没少，只是绕了个弯。** 所以"消融一个 CLI 工具"必须是严格的：
还得把 `run_shell` 一起摘掉。

> 这也是为什么评测轨迹**必须记录工具参数**。
> 之前轨迹里 `args` 恒为空对象，只能看到"调了 36 次 run_shell"，
> 分不清跑的是 `ls` 还是 `grep` —— 而这两种结论完全相反，不能靠猜。
> 修掉之后（`src/eval/runner.ts` 的 `summarizeArgs`），一眼就能看出问题。

### 结论三：⭐⭐ 就算不能执行任何命令，agent 也能全过

摘掉 `grep` + `run_shell` 之后，agent 只剩「读文件 / 找文件 / 改文件」，
**一次命令都跑不了** —— 它没法跑 `tsc`、没法跑 `node test/run-all.js`。

结果仍然是 **28/28 全过、0 回归**。

它是怎么做到的：
- 31 号题（真跑 tsc）：**纯靠读类型定义推理出该改哪几行**，
  check.js 里的 tsc 自己跑，验证的是真实类型错误 —— 所以它改对了
- 34 号题（性能）：直接推理出"每次都在 toLowerCase，应该缓存"，
  加了缓存就够
- 35 号题（静默破坏）：读出 `sendSms` 的 try/catch 是承重墙，
  新功能复用 `sendSms` 就不会破坏契约

**这说明这 5 道题考的是「代码理解 + 推理」，不是「工具使用」。**

---

## 3. 这个结论指向下一步该做什么

如果想让这套题能区分"会搜索的 agent"和"不会搜索的 agent"，
得让**规模**成为瓶颈，而不是让**陷阱**成为瓶颈：

| 做法 | 效果 |
|---|---|
| 沙箱塞 50+ 个文件，调用点散落在 5-6 个目录 | agent 必须靠搜索，不能通读 |
| 调用点藏在 3 层 re-export 链后面 | grep 一次找不到 |
| 同一函数在 10+ 处被调用，其中 2 处是动态 require | 漏一处就挂 |

**这是 Phase 2 之后最该做的题库升级方向**，已记进 `ROADMAP.md`。

---

## 4. 附带发现：grep 这个工具可能是在帮倒忙

摘掉 grep 后成本反而**降了 25%**（¥1.57 → ¥1.18），轮数也降了（79 → 71）。

⚠️ 但这是单次运行的结论，噪声能到 3%，**必须用 `--repeat 3` 复跑确认**：

```bash
npm run eval -- --repeat 3 31 32 33 34 35
```

如果结论成立，那"精简工具集"就是一个能省钱的方向 ——
而这正好是这个项目一贯的思路：**不是加功能，是让每一分 token 都花在刀刃上**。
