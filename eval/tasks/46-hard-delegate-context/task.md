# 任务：找出所有调用了 `formatUserId` 的地方

## 背景

`src/core/user-id.js` 里有一个 `formatUserId(user)`，负责把用户对象渲染成统一的显示串。

我要做一次影响面评估：**改它的输出格式之前，得先搞清楚哪些地方真的调了它。**

## 你要做的

给我一份调查结论，说清楚两件事：

1. 一共**多少处**调用；
2. 分别在**哪些文件**里（给出文件路径）。

## 仓库结构

```
src/core/user-id.js   formatUserId 的定义
src/handlers/          60 个 handler 文件，彼此基本不相关
```

## 注意

- 我只要一份**调查结论**，**不要改任何代码**。这个仓库现在的状态就是对的。
- `src/handlers/` 下面有 60 个文件。**别自己一个一个读** —— 那样会把你的上下文塞满，
  而且读到最后你手里只剩一堆文件内容，没有结论。找个合适的办法，
  **只把结论带回来**。
- 只算**真正的调用**：文件里只是在注释里提到过 `formatUserId`，
  或者只是把它当字符串用了一下的，**都不算调用点**。

## 完成标准

`check.js` 会断言：

1. 你的结论里点名的文件，覆盖了绝大多数真正调用 `formatUserId` 的文件（漏几个不算，
   但关键的几个不能漏）；
2. 你没有把"注释里提到"的文件也算成调用点；
3. `formatUserId` 自己的行为没被改坏，仓库里一个文件都没被动过；
4. 你是**拿到结论**的，而不是把 60 个文件挨个读进自己的上下文；
5. 这项调查确实交给了子智能体去做。

> 这道题在考什么：**上下文隔离。**
>
> 主 agent 的上下文是一张共享的桌子，放得下 20 页卷宗，但活儿可能有 300 页的量。
> 自己读 60 个文件，桌子就满了 —— 而且满的全是没用得上的中间过程，
> 真正需要的那句结论反而被挤掉了。
>
> 子智能体的价值就是把中间过程隔离掉：它自己去翻，
> 最后只递回来一份报告。这就是为什么这道题不只看"答对没答对"，
> 还要看"你是怎么查的"—— 一个把 60 个文件读进自己上下文的 agent，
> 哪怕最后结论对了，这条路在真实仓库上也走不通。
