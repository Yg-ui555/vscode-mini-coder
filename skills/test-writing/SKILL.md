# 写单元测试的规范

## 一条铁律：一个测试只断言一件事

一个测试里塞五个断言，意味着它失败时你还要再查一遍才知道是哪件事坏了。

```js
// ✗ 失败时不知道是哪个坏了
it('用户功能', () => {
  expect(user.name).toBe('张三');
  expect(user.age).toBe(30);
  expect(isAdmin(user)).toBe(true);
});

// ✓ 一眼就知道
it('用户名正确', () => { expect(user.name).toBe('张三'); });
it('年龄正确', () => { expect(user.age).toBe(30); });
```

## 测试名要写成一句话

`it('add 遇到负数时应返回 0')` 比 `it('test add')` 有用得多 ——
失败报告里那一行就是你唯一的线索。

## 每个功能至少要有一个失败用例

全是通过的测试套件，说明**什么都没测**。

按重要性排，最该覆盖的是：

1. **边界值**：`0`、`-1`、空字符串、空数组、超长输入
2. **异常输入**：`null` / `undefined` / 类型错误
   —— 用户输入的东西永远比你预期的脏
3. **正常路径**：最后写，前两类都过了再说

## 别测实现细节，测行为

```js
// ✗ 测内部实现，重构一下就挂了，但它测不到任何真实问题
expect(calculator._add(a, b)).toBe(3);

// ✓ 测对外行为，重构不会误报
expect(calculator.add(1, 2)).toBe(3);
```

## 怎么判断测试到底跑了没有

**不要用 `output.includes('passed')` 判断测试通过。**

pytest 失败时的输出是 `3 failed, 5 passed` —— 这一行里就有 "passed"，
用字符串匹配会导致"测试明明挂了却判定通过"。

正确做法是看**退出码**：`0` 表示全过，非 `0` 表示有失败。

## 改代码后的自检顺序

1. 改完代码
2. 跑**相关**测试（不是全量，除非项目很小）
3. 红了 → 回到 debug-workflow
4. 绿了 → 再跑一次全量，确认没破坏别处

**第 4 步最容易省，也最容易出事**：把别的测试改红了是 AI 编程助手
最典型的失败方式，而且它自己发现不了 —— 它跑一次测试看到绿色就收工了。
