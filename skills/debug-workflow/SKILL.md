# 系统化排查流程

改代码之前，先把"到底哪里坏了"搞清楚。跳过这步直接改，
是在赌，赌错就是白改一轮还引入新问题。

## 1. 先复现

拿到一个 bug，先让它稳定出现。

- 有测试覆盖 → 跑那个测试，让它红给你看
- 没有测试 → 写一个最小复现（能稳定触发即可，不需要漂亮）

**不要跳过这步。**"我大概知道是哪的问题"是所有返工的开始。

## 2. 读错误信息，从最具体的那条开始

报错信息里通常有一条真正的原因，其余都是噪音：

- `EISDIR` → 你在对目录调文件操作
- `ENOENT` → 路径不存在（注意相对路径是相对**工作区根**解析的）
- `SyntaxError` → 上一个改动引入了语法错误，看报错行号
- 类型错误 → 注意 null / undefined，多数"莫名其妙"的报错源于此

## 3. 定位：用搜索而不是通读

通读一个大文件比你想的贵得多。

```
grep 关键函数名 / 错误信息里的关键词
→ 缩小到几个候选文件
→ 只读这几个
```

文件很多时先用 glob 按名字过滤，比 grep 更快。

## 4. 只有一个假设，一次验证

不要同时改三处然后一起测 —— 出问题时你不知道是哪一处。

改一处 → 跑测试 → 看结果 → 再改下一处。

## 5. 改完确认没有破坏别处

改完跑一次相关测试。跑全量测试也行（慢但保险）。

## 常见反模式

| 反模式 | 为什么有害 | 该怎么做 |
|---|---|---|
| 改完不测 | 不知道有没有修好，也不知道有没有弄坏别的 | 每次改完都跑相关测试 |
| 一次改多处 | 出问题不知道是哪处引起的 | 一次改一处 |
| 删掉报错 | 报错消失 ≠ 问题解决，可能是被吞了 | 先理解为什么报这个错 |
| 注释掉失败代码 | 问题还在，只是看不见了 | 找到真正原因 |
| 加 try/catch 吞异常 | 同上，且更难查 | 至少 log 出来 |

## 记录

排查过程里如果有"非显然"的发现（比如某个命令在这台机器上不工作），
用 `record_note` 记下来。下次遇到同一个坑能省下时间。
