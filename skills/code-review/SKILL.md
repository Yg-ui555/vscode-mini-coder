# 交付前自检清单

改完代码、报告结果之前，逐条过一遍。

## 改对了没有

- [ ] 真的重新读了一遍改动后的文件（而不是凭记忆）
- [ ] 用户要的是**这个**吗？不是相近的另一个？
- [ ] 有没有把需求理解错了还改了多处？

## 有没有破坏别处

- [ ] 相关测试跑过了，**而且是绿的**（看退出码，不看有没有 "passed" 字样）
- [ ] 改动有没有影响到调用方？（改了函数签名 → 所有调用点都要检查）
- [ ] 有没有留下没用的变量 / import / 死代码？

## 边界情况

- [ ] 空输入（`""`、`[]`、`{}`、`null`）会怎样？
- [ ] 出错时会怎样？是崩溃、静默失败，还是用户能看懂？

**静默失败是最坏的** —— 用户看不到错误，只会觉得"这功能时好时坏"。

- [ ] 路径相关：相对路径是相对**工作区根**解析的，不是 `process.cwd()`

## 报告

- [ ] 说清楚**改了什么**（哪些文件、什么变化）
- [ ] 说清楚**为什么这么改**（放弃了哪些方案，为什么）
- [ ] 不确定的地方**明说**，不要含糊过去

❌ "已优化性能"
✅ "把嵌套循环换成哈希查找，查找从 O(n²) 降到 O(n)。10 万条数据下从 2.3s 降到 8ms"

## 最后一条

如果这次改动里有**非显然的发现**（某个命令在这台机器上不工作、
某个库的用法和文档不一致），用 `record_note` 记一条。

这类知识下次遇到能直接省时间，而它是整个开发过程里最容易丢失的东西。
